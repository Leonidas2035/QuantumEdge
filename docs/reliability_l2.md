# L2 Reliability contract

## Why L2 is special

L2 streams (fills, positions, equity, risk, etc.) are generated by Executors/Bots and feed longer-lived systems such as QuestDB analytics and reporting. Unlike the Hot Path (L1) we **never drop** L2 events. Every record is serialized to a WAL (spool) before we attempt to push it into QuestDB; if QuestDB is unreachable or overloaded we keep the spooled copy and replay it later.

## Envelope schema

Each spooled/read event is a JSON object that matches `MarketDataHub.models.L2Envelope`:

- `ts_ns`: nanosecond timestamp (source of truth for ILP lines)
- `entity`: logical stream (`fills`, `positions`, `equity`, `risk`, etc.)
- `symbol`: optional; used for symbol-scoped state updates
- `seq` / `event_id`: sequence number or UUID for idempotent replay
- `source`: origin identifier (bot name, service)
- `schema_ver`: versioned schema to guard replay
- `payload`: JSON-friendly dict with data such as FillEvent, PositionEvent, etc.

Payload structs exist for the common gradients: `FillEvent`, `PositionEvent`, `EquityEvent`, `RiskEvent`. Extra keys can be stored in `payload` and later stored in `payload_json`.

## Table mapping (entity -> QuestDB table)

| Entity | Table | Notes |
| --- | --- | --- |
| `fills` | `l2_fills` | Columns cover order_id/side/qty/price/fee/pnl/exchange/account plus JSON payload backup. |
| `positions` | `l2_positions` | Captures entry/mark/unrealized data + JSON payload. |
| `equity` | `l2_equity` | Tracks equity/balance/available per `currency`. |
| `risk` | `l2_risk` | Logs risk_mode/exposure/max_dd with optional notes. |

Each table is partitioned by `DAY`, designated the `ts` timestamp column, and includes `source`, `seq`, `event_id`, and `payload_json` to help replay logic deduplicate or examine raw data.

## At-least-once semantics

- Every L2 append writes the envelope to disk before trying QuestDB. The spool directories are organized by day/hour (`spool/l2/YYYY-MM-DD/HH/*.jsonl.gz`) with rotation at ~64 MB.
- A replay cursor file (`spool/l2/.replay_state.json`) remembers progress so replays can resume without redelivering already ingested data.
- Duplicates can occur (the same envelope re-sent after replay), but missing records are unacceptable.
- L0/L1 may still drop under pressure; only L2 uses the WAL guarantee.
