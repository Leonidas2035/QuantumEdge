Нижче — пакет для “скальп-бота” (tick): 25 сценаріїв/епізодів, переоцінка ML-модуля, дорожня карта ML, і що саме логувати через Supervisor.

1) Формат “епізоду” (щоб бектести були як реальні кейси)

Episode = вирізка тіку з чіткими межами й тегом сценарію.

Структура:

scenario_id

t0…t1 (час початку/кінця)

pre_roll 30–120с (контекст до події)

event_window 10–180с (власне сценарій)

post_roll 30–120с (наслідки)

meta: spread, vol, trade_rate, ofi, liq_spike, regime_tag

Що треба з тіку:

price, qty, side (або isBuyerMaker), ts

бажано: top-of-book bid/ask + depth (інакше скальп буде “сліпий” до спреду)

2) 25 типових сценаріїв (tick-level, під скальп)

Кожен сценарій = правило детекції + рекомендована довжина епізоду.

A. Флет / mean-reversion (основа скальпу)

Micro-range 0.15–0.35%: ціна коливається в вузькому каналі, vol_low, spread_ok (120–600с)

VWAP ping-pong: часті перетини VWAP, відскоки від ±1σ (120–900с)

Band touch + revert: торкання VWAP −2σ / +2σ і повернення всередину (60–300с)

Orderflow flip: OFI змінює знак, ціна не пробиває діапазон (30–120с)

Liquidity wall bounce: кілька ударів в рівень (мікро-рівень) і відскок (30–180с)

B. Імпульс → затухання (для FREEZE/UNFREEZE логіки скальпу)

Impulse up 0.6–1.2% за 5–20с (pre/post 60–120с)

Impulse down 0.6–1.2% за 5–20с

Volatility expansion: різкий ріст trade_rate + spread_widen (30–120с)

Volatility contraction: після імпульсу trade_rate падає, спред нормалізується (60–300с)

Stop-run wick: швидкий прокол рівня і моментальне повернення (10–60с)

C. Fakeout / breakout (критичні для “не ловити ножі”)

Breakout + retest: пробій діапазону 0.4–0.8% і повернення на ретест (120–600с)

False breakout: пробій <30с і повне повернення в канал (60–180с)

Trend start: серія HH/HL + OFI підтверджує (180–900с)

Trend exhaustion: ціна росте, але OFI слабшає / об’єм падає (120–600с)

Chop / whipsaw: часті зміни напряму, багато “шумових” сигналів (300–1200с)

D. Мікроструктура: спред/ліквідність/ковзання (execution-реалізм)

Spread blow-out: спред > X bps, depth падає (10–60с)

Thin book: depth < порогу, ціна “стрибає” на малих об’ємах (60–300с)

Slippage trap: ринкові ордери гіршають vs mid (симулятором) (60–180с)

Burst trades: потік угод у 3–10× швидше норми (10–60с)

Iceberg-like absorption (наближено): багато дрібних угод в рівень без проходу ціни (30–180с)

E. Біржові/ф’ючерсні події (під Supervisor і ризик-режими)

Funding window: 5–15 хв до/після funding часу (600–1800с)

Mark-price divergence: mark відхиляється від last (120–600с)

Liquidation spike: сплеск force-orders (якщо беремо WS) (10–120с)

Post-liq revert: після ліквідацій ціна повертається до VWAP (60–300с)

UTC day reset effect: зміна добового VWAP, зміна активності (600–1800с)

3) Переоцінка ML модуля (що варто допиляти під скальп)

По поточній структурі ML у боті є (signal_model + online_features + train), але під скальп критично допрацювати:

Жорстке вирівнювання online/offline: один feature builder, одна схема, один шлях даних (щоб модель не “бачила інше” у live).

Train/val/test + walk-forward (без цього метрики “брешуть”).

Multi-horizon саме для скальпу: h=1s, 5s, 15s (або 1/5/30 тік-барів) і агрегатор умов входу.

Калібровка ймовірностей (інакше p_up = 0.57 сьогодні ≠ 0.57 завтра).

Фічі мікроструктури (мінімум):

OFI / buy-sell imbalance

trade rate, volume spikes

spread, top-depth, micro-vol (реалізована вола на 1–5с)

VWAP deviation (z-score від VWAP/AVWAP)

Відмова від важкого I/O у hot loop: пер-тік JSON/часті записи = лаги → поганий скальп. Писати батчами (Parquet/файли по хвилині).

4) Дорожня карта впровадження ML (етапами)
Етап 1 — Дані (1 пара, tick)

Підключити реальний стрім: trades/aggTrades + depth(top)

Уніфікувати схему тіку, додати side / isBuyerMaker

Зробити EpisodeCutter: нарізка 25 сценаріїв у датасет

Етап 2 — Базові лейбли (без “магії”)

Лейбл для кожного тіку/стану: ret_{1s,5s,15s} або ret_{N ticks}

Мітки: up/down/flat + “no-trade” (коли спред/ліквідність погані)

Етап 3 — Модель-фільтр входу (MVP)

Навчити просту модель (XGB/LightGBM) по multi-horizon

В DecisionEngine: торгувати лише якщо p_up(h1,h5,h15) узгоджені + guard по спреду/глибині

Етап 4 — Режими + Supervisor

Окрема модель/правила regime classifier: RANGE / TREND / PANIC

Supervisor перемикає:

scalp-режим (лише RANGE)

FREEZE (PANIC)

throttle частоти угод

Етап 5 — Моніторинг дрейфу

щоденні звіти: метрики моделі, частка пропущених угод, drift фічей

авто-перенавчання по останніх N днів (offline), деплой моделі через manifest+hash

5) Лог-статистика через SupervisorAgent (що саме додати)

6) Дані з біржі через ccxt/ccxt.pro

Так, можна. Практично:

ccxt.pro — зручно, але може бути повільніше за нативний WS.

Для скальпу часто краще напряму Binance WS (trades+depth), а ccxt лишити для REST (синхронизація/баланси/ордера).

Пропозиції/зауваження (коротко)

Для скальпу обов’язково мати bid/ask + depth — без цього ML/guards “в вакуумі”.

Епізоди (25 сценаріїв) — це база для швидкого навчання Supervisor без місяців демо.

“Замок” тримаємо окремо, як і домовились; у цьому плані він не змішується зі скальп-логікою.

Якщо ок — наступним кроком я можу:

дати точні пороги детекції для кожного з 25 сценаріїв (у bps/%/секундах),

і шаблон EpisodeCutter конфігу (yaml/json), щоб Codex швидко реалізував.
