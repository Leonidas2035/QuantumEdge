Етап 5 — CPU-план під i7-14700: P-cores, без HT, лише потрібна кількість

Ціль: мінімальна латентність + контроль ресурсів, без “розмазування” по E-ядрах і HT.

5.1. Вимкнути HT “по-справжньому”

Найкраще: вимкнути Hyper-Threading у BIOS (щоб ОС навіть не бачила sibling threads).

Якщо HT поки лишається: не використовувати sibling threads (вибір CPU по topology).

5.2. Розділити потоки на ролі

Рекомендований розподіл:

Критичний шлях (market data → decision → execution): 2–4 P-cores

ML/feature builder/backtest/лог-аналітика: решта (може навіть частина E-cores)

Supervisor API/monitoring: 1 P-core або E-core

5.3. Реалізація (без “магії”)

systemd:

CPUAffinity= або AllowedCPUs= (cgroups v2)

приклад ручного запуску:

taskset -c 0-3 python QuantumEdge.py start


Для точного відбору P-cores: зчитати /sys/devices/system/cpu/cpu*/topology/* і побудувати мапу.

Готово, якщо: процеси стабільно “сидять” на вибраних CPU, а p99 latency по циклу рішення знижується.

Codex-задача: “додати cpu_affinity в конфіг + реалізацію pinning для Supervisor/бота (Linux only), без поломки Windows-legacy”.

Етап 6 — GPU-план під RTX 4060: що реально варто переносити

Ключова ідея: GPU має сенс там, де є важка математика або батчі. Для tick-by-tick маленьких операцій overhead PCIe може з’їдати вигоду.

Переносимо на GPU (високий профіт)

ML inference, якщо це нейромережа/torch/onnx і модель не мікроскопічна.

ML training (тут виграш майже завжди).

Бектести/симуляції, якщо можна батчити (векторизовано, великий масив даних).

Лишаємо на CPU (критично по latency/IO)

WebSocket/мережа, order placement/cancel, risk-engine, state machine — це I/O та бізнес-логіка.

Стек (практично)

Torch CUDA або ONNX Runtime (CUDA) — для inference.

За потреби: TensorRT (але це окремий рівень складності).

Готово, якщо: GPU завантажується тільки там, де це дає приріст, і не додає затримки в критичному циклі.

Codex-задача: “додати абстракцію InferenceBackend (cpu/onnx_cuda/torch_cuda), автодетект GPU, конфіг перемикач”.
