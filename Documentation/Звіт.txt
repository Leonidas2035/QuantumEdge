--------------------------------------------------------------------------------
БЛОК 1: ОЧИЩЕННЯ ТА DATA RETENTION (УТРИМАННЯ ДАНИХ)
--------------------------------------------------------------------------------

QuestDB оптимізована під додавання (append-only) та видалення даних цілими
партиціями (командою DROP PARTITION). Для уникнення переповнення диска та
забезпечення швидкої роботи бектестів встановлюються такі політики retention:

1. Сирі тіки (trades):
   - Зберігаються: 7 днів.
   - Партиціювання: BY DAY.
   - Обґрунтування: Достатньо для аналізу мікроструктури ринку за тиждень та швидких
     локальних тестів.

2. Знімки стакану (orderbook_snapshots / depth_l2):
   - Зберігаються: 3 дні.
   - Партиціювання: BY DAY.
   - Обґрунтування: Найбільш "важка" таблиця. Зберігання більше 3 днів призведе до
     невиправданого навантаження на SSD.

3. Хвилинні свічки (klines):
   - Зберігаються: 90 днів.
   - Партиціювання: BY MONTH.
   - Обґрунтування: Використовуються Hermes для середньострокового аналізу трендів
     та оцінки ринкових режимів.

4. Обмеження диска (Disk Budget):
   - Виділений ліміт SSD: 50 ГБ.
   - Процес очищення реалізується через cron-скрипт або внутрішній фоновий сервіс,
     який виконує запити виду:
     `ALTER TABLE <table_name> DROP PARTITION LIST <partition_name>;`

--------------------------------------------------------------------------------
БЛОК 2: FEATURE STORE (УНІФІКОВАНА ТАБЛИЦЯ ІНДИКАТОРІВ)
--------------------------------------------------------------------------------

Для виключення створення окремих таблиць під кожного бота впроваджується концепт
уніфікованої таблиці `market_features`. 

- Частота запису: 1 раз на секунду (1 Hz) в режимі реального часу.
- Об'єм записів: 86,400 рядків на добу на один символ.

DDL Схема для створення таблиці `market_features`:
```sql
CREATE TABLE market_features (
    timestamp TIMESTAMP,
    symbol SYMBOL,
    mid_price DOUBLE,
    spread DOUBLE,
    atr_14 DOUBLE,
    rsi_14 DOUBLE,
    macd_line DOUBLE,
    macd_signal DOUBLE,
    vwap_daily DOUBLE,
    bb_upper DOUBLE,
    bb_lower DOUBLE,
    ofi_raw DOUBLE,
    volume_delta DOUBLE,
    buy_sell_ratio DOUBLE
) TIMESTAMP(timestamp) PARTITION BY DAY;

-- Створення індексу для швидкого пошуку за інструментом
ALTER TABLE market_features ALTER COLUMN symbol ADD INDEX;
```

--------------------------------------------------------------------------------
БЛОК 3: ВЗАЄМОДІЯ БОТА З БАЗОЮ (ЛАТЕНТНІСТЬ VS КОНСИСТЕНТНІСТЬ)
--------------------------------------------------------------------------------

Для вирішення проблеми затримки (latency) при HTTP SQL запитах обрано наступну гібридну схему:

1. Для HFT Scalper Bot:
   - Схема: Варіант А (Тільки синхронізація при старті).
   - Опис: Бот при запуску робить один HTTP-запит до QuestDB, щоб заповнити свій
     in-memory буфер (останні 1000 тиків/фіч) для прогріву моделей (warmup). Після
     цього він працює виключно за рахунок отримання швидких повідомлень через ZMQ
     (порт 5555) від MarketDataHub, що забезпечує нульову затримку запитів до БД.

2. Для Dynamic DCA Bot:
   - Схема: Гібрид Варіантів А та Б.
   - Опис: Бот прогрівається при старті (Варіант А), а також здійснює періодичні
     запити (Варіант Б) раз на 5 хвилин для отримання історичної волатильності
     (ATR за тривалий час) та профілю об'ємів (Volume Profile) з метою перерахунку
     параметрів сітки та визначення зон підтримки/опору.

--------------------------------------------------------------------------------
БЛОК 4: СХЕМИ ДЛЯ ТЕЛЕМЕТРІЇ ТА АУДИТУ
--------------------------------------------------------------------------------

Для відображення стану системи на дашборді та аналізу поведінки ботів з боку Hermes,
створюються дві системні таблиці:

1. Уніфікована таблиця телеметрії ботів (`bot_telemetry`):
```sql
CREATE TABLE bot_telemetry (
    timestamp TIMESTAMP,
    bot_id SYMBOL,
    status SYMBOL,
    pnl_session DOUBLE,
    active_margin DOUBLE,
    drawdown_pct DOUBLE,
    latency_ms INT
) TIMESTAMP(timestamp) PARTITION BY DAY;

ALTER TABLE bot_telemetry ALTER COLUMN bot_id ADD INDEX;
```

2. Таблиця аудиту рішень Hermes (`llm_decisions`):
   Ця таблиця зберігає лог дій глобального агента, що дозволяє проводити розслідування
   екстрених зупинок (Kill Switch) та коригувань лімітів ризику.
```sql
CREATE TABLE llm_decisions (
    timestamp TIMESTAMP,
    decision_id SYMBOL,
    verdict SYMBOL, -- PAUSE, RESUME, ADJUST_LIMIT, HALT
    reason STRING,
    raw_prompt STRING,
    raw_response STRING
) TIMESTAMP(timestamp) PARTITION BY DAY;
```
